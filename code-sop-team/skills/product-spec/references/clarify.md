# 澄清四问与用户故事

## 一、澄清四问（缺一个就别排期）

1. **谁**：具体到一类人，不是"用户"。他们现在怎么凑合解决？
2. **什么问题**：不做的代价是什么？说得出代价才说明是真需求。
3. **什么算解决**：一句话可判定的结果状态。
4. **什么时候要**：硬期限还是"越早越好"？硬期限会改变切法。

四问答不全 → **不要替用户编答案**，把缺口原样交回主理人去问。编出来的需求比没有需求更贵。

### 追问技巧

| 用户说的 | 追问什么 |
|---|---|
| "用户想要导出" | 谁要导？导出来给谁看？现在手抄吗？ |
| "要快一点" | 现在多慢？多快算快？慢的代价是什么？ |
| "做个后台" | 谁登录？他每天第一件事想看到什么？ |
| "和 X 差不多" | X 的哪一部分？那一部分你自己用起来舒服吗？ |

## 二、用户故事（一句话规格）

格式：`作为 <谁>，我要 <做什么>，以便 <得到什么价值>`。

写完之后必须能回答：

- 这个故事的**反例**是什么？（什么情况下它不成立）
- 不做它，用户会退回到哪个凑合方案？

故事只写"要什么价值"，**不写实现**。出现"用 Redis 缓存"这类词，说明写成了技术方案，删掉。

### 好故事与坏故事

| 坏 | 为什么坏 | 好 |
|---|---|---|
| 作为用户我要一个导出按钮 | 没有"以便"，不知道价值 | 作为运营，我要导出本周订单为 CSV，以便直接导入对账系统不用手抄 |
| 作为用户我要用 Redis | 技术方案冒充需求 | 作为访客，我要页面 1 秒内打开，以便不流失 |
| 作为管理员我要权限管理 | 粒度不明 | 作为管理员，我要只让组长看到本组数据，以便不越权泄露 |
