# MVP 切法与范围谈判

## 一、MoSCoW

| 级别 | 含义 | 处理 |
|---|---|---|
| **Must** | 不做就不能上线 | 全部进本次 Sprint |
| **Should** | 很重要但有凑合方案 | 进 Sprint，可延后一个 Sprint |
| **Could** | 有更好，没有也行 | 进候选，不排期 |
| **Won't** | 本次明确不做 | 写进 **Out of scope**，防漂移 |

切的时候问一句：**"如果只做一条 Must，是哪条？"** 答不出来说明还没想清优先级。

### 判断"是不是 Must"的三个条件（全中才是）

1. 没有它，用户的核心任务**做不到**（不是做得不爽）。
2. 没有它，上线会**出事**（数据错、安全事故、合规）。
3. 没有它，后面的事**全部要重做**（架构地基）。

只满足"老板说要"或"竞品有"→ 进 Should，不进 Must。

## 二、Out of scope 的写法

不是写"暂不做"，要写**为什么不做 + 什么时候再看**：

| 弱 | 强 |
|---|---|
| 暂不支持多语言 | 不做多语言：本期只有中文用户，且 i18n 会拖慢 2 周；若 3 个月内有海外需求再立 Epic |
| 性能优化以后再说 | 不做缓存层：当前 p95 180ms 已达标；若超 500ms 再立 SPIKE |

**Out of scope 是防止范围漂移的唯一凭据。** 用户中途说"这个也加上"，拿它对齐。

## 三、范围谈判（需求中途变多时）

用户加需求时，不说"做不了"，也不直接接。给三选一：

| 选项 | 代价 | 适用 |
|---|---|---|
| 加进来 | 当前 Sprint 延期 / 砍掉某条 Should | 新需求确实更高价值 |
| 换掉 | 用新需求替换一条同级需求 | 总量不变、优先级变化 |
| 排下一个 | 进候选表，不动当前 Sprint | 不急、或依赖未定 |

把选择权和代价一起摆出来，由用户拍板。**不要自己替用户砍需求，也不要默默加班。**

### 常见话术

- 「这条可以做，代价是本 Sprint 的筛选功能要往后挪一个 Sprint，或者砍掉导出。您选哪个？」
- 「先加进候选表，等这版验完再排——因为它依赖的登录改造还没做，现在做会返工。」

## 四、和规划师的交接

产品经理交的是「做什么 + 什么算对 + 优先级」，规划师接的是「怎么切。**不交切法**，避免两人对任务粒度各有一套说法。
