# 验收标准可执行化

**这是本 skill 价值最高的一节。** 验收闸（`task-verify`）只认两种写法：可执行命令、`manual:` 声明。其余一律 `fail-closed` 直接 FAIL。

## 一、从"功能正常"到可执行

| 原始说法（无效） | 改写后（有效） |
|---|---|
| 「导出功能正常」 | `` `python -m pytest tests/test_export.py -q` `` 或 `manual: 打开 /orders → 筛选本周 → 导出 CSV，行数 = 7，复核人+截图` |
| 「页面不报错」 | `` `npm run build` `` + `manual: 打开 /dashboard，控制台无 error，截图` |
| 「性能可以」 | `` `python scripts/bench.py --limit 1000` `` 输出 p95 < 300ms（命令 + 阈值） |
| 「权限对了」 | `` `pytest tests/test_auth.py -q` `` 覆盖 4 个角色 × 3 个端点 |
| 「迁移没问题」 | `manual: 在副本库跑 up → 校验行数一致 → 跑 down → 表结构与迁移前 diff 为空` |
| 「文档写好了」 | `manual: README 含快速开始三命令，新人照做能跑起来，复核人签名` |

## 二、三条改写规则

1. **给命令**：能自动判定的，优先写测试命令，不写人工核对。
2. **给阈值**：涉及数量、时间、大小的，必须带数字。"快""稳""够用"不是标准。
3. **给路径**：人工验收要写清「打开哪 → 操作什么 → 看到什么 → 证据存哪 → 谁复核」。

## 三、拆到"一件事"

**一个验收标准只能验一件事。** 出现"且""并且""同时"就拆成两条。

| 拆前 | 拆后 |
|---|---|
| 「能登录且权限正确」 | ① 登录成功返回 token ② 角色 A 看不到角色 B 的数据 |
| 「导出 CSV 且格式正确」 | ① 行数 = 7 ② 表头字段顺序与模板一致 |

理由很实际：合在一起失败时，`task-verify` 只给你一个 FAIL，你不知道坏在哪一层。

## 四、`manual:` 的写法（严谨到能被第三方复核）

格式：`manual: <打开什么> → <做什么> → <看到什么> → <证据存哪> → <谁复核>`

- **看到什么**必须是可判定的："页面正常"不行，"列表首行显示订单号、状态列为已支付"行。
- **证据**要有位置：截图路径、日志片段、导出文件名。留证时把这些写进 `--evidence`。
- 复核人写角色（如"由主理人复核"），不写"自己看过了"。

## 五、自检

写完一组验收标准，逐条问：

1. 换个人来执行，会不会得到同一个结论？
2. 这条失败时，我能不能立刻知道坏在哪一层？
3. 有没有一条是"我觉得应该没问题"？——有就重写。
