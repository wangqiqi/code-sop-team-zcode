# 异常 · 边界 · 兜底手册（Failure Playbook）

Happy path 由 SOP 正文覆盖；本文件覆盖**非 happy path**：工具失败、输入畸形、并发冲突、成员缺席、用户中断、以及所有「跑不通时该怎么办」。

**总原则（三条，不可打折）**

1. **fail-closed**：判定不了 = 不通过。宁可 BLOCK，绝不静默放行。
2. **信号可信**：没有真实命令输出就没有「通过」；没有成员原文输出就没有「成员结论」。禁止伪造闸门输出、禁止替成员发言。
3. **降级要声明**：工具缺失导致软约束时，必须**显式告知用户当前是降级模式**、缺什么、影响是什么；不得让对方误以为硬约束仍在生效。

---

## 一、退出码与语义

| rc | 含义 | 主理人动作 |
|----|------|-----------|
| 0 | OK / PASS | 可以继续下一步 |
| 1 | BLOCK / FAIL | 停下，按本手册定位修复；**不得**标 ✅ / commit / 收口 |
| 2 | 参数 / 环境错误 | 修正命令或环境后重跑，不是「任务失败」 |
| 3 | MANUAL-PENDING | 人工验收未留证；核对后带 `--evidence` 重跑，不是 PASS |
| 130 | 用户中断 | 不视为 PASS；确认中断点后重跑验收 |

任何非 0 都不得继续编码。**`--force` 只用于用户明确接受残项的逃生口，必须在汇报中写明跳过了什么。**

## 二、闸门脚本异常矩阵

| 症状 | 判定 / 输出 | 兜底与修法 |
|------|------------|-----------|
| 找不到 `sop_gate.py` | 脚本定位三级探测全失败 → 退出 2 | 检查插件安装路径；设 `SOP_GATE=<绝对路径>`；**不得**手写假输出代替闸门 |
| 普通 Windows 没有 `python` 命令 | **正常现象**：Windows 不自带系统级 Python；`python` 可能只是 Microsoft Store 占位 | 在 ZCode 会话里直接用当前解释器（本 skill 示例中的 `python` 就指它）；用户自己的终端里装官方 Python 3.8+，或用解释器绝对路径调用 |
| 会话解释器不在 PATH | `python3`/`python` 都找不到，但当前会话本身能执行 Python | `install-hook` 已内嵌安装时的解释器绝对路径，钩子照常硬拦；手动跑闸门时用绝对路径调用；`doctor` 会显示探测到的解释器 |
| 内嵌解释器失效且 PATH 也无 Python | `doctor` 报 FAIL「钩子解释器失效」；git 钩子**告警后**软降级放行 | 重装 hook 重新定位；在此期间声明「软约束降级模式」，不得声称全流程闭环 |
| 插件移动 / 钩子脚本路径失效 | `doctor` 报 FAIL「钩子脚本路径失效」（不再只看到「钩子已安装」就报 OK） | 重跑 `install-hook` 写入新路径；在此之前不得把钩子当作硬闸 |
| `--root` 或 `SOP_PROJECT_ROOT` 指错 | rc=2，明确报路径不存在 | 改正路径或清掉环境变量；**不会**静默退回 cwd（那会改错项目） |
| `plan.md` 不存在 | init 前所有闸 FAIL / BLOCK | 主理人跑 `init` → 规划师写 plan |
| `plan.md` 是目录 / 权限异常 / 编码损坏 | 读取按空处理并 WARN，闸 fail-closed；不再 Traceback | 修路径/权限后 `doctor` 复核；必要时从备份重建 plan |
| `PLAN_APPROVED` 是 `hacked`/`true`/空 | `gate-check` BLOCK（只认 `YYYY-MM-DD`） | 由规划师完善 plan → 用户确认 → 重新 `approve`，不要用 `set` 伪造批准 |
| 重复 TASK ID | `plan-check` / `verify` FAIL，列出重复 ID | 删掉重复行或改 ID；重新 `plan-check` |
| 状态格同时有 `⬜ ✅` | 状态歧义 → FAIL | 只保留一个状态标记，重新验收后再标 ✅ |
| 验收列是描述性文字 | `task-verify` FAIL | 改成可执行命令或 `manual:` + 证据要求；可派 qa-engineer |
| 多个反引号（路径 + 命令） | 优先挑像命令的那段；无法判断则 fail-closed | 验收列只保留**一条**反引号命令；路径写进 Target 列 |
| `manual:` 无证据 / 证据是空白 | rc=3 MANUAL-PENDING | 核对后 `--evidence "复核人+路径+步骤"` 重留；Acceptance 一改旧证据即失效 |
| `evidence.json` 损坏 | 按空证据处理 → rc=3；`doctor` 报「内容损坏」 | 备份后删除损坏文件，重新留证；不要直接编辑 JSON 绕过 |
| 验收命令超时（watch/交互/死循环） | 杀整棵进程树，判 FAIL，rc=1 | 改 CI 非交互模式；确需更长设 `SOP_VERIFY_TIMEOUT=<秒>`，`0` 不限；超时值越界会钳制并 WARN |
| 用户 Ctrl+C | 子进程一并终止，rc=130，不判 PASS | 确认中断位置，重跑该任务验收 |
| 状态文件被并发写（多会话/多团员） | `.lock` 原子锁保护读-改-写；拿不到锁 rc=1 并提示 | 稍后重试；超过 120s 的锁视为崩溃残留自动清理；必要时人工删除 `.zcode/sop/.lock` |
| 磁盘写入失败 / 文件被占用 | 短重试后明确报 INTERNAL-ERROR，rc=1 | 关闭占用该文件的编辑器/杀软，重跑；**不会**假装写入成功 |
| `.gitignore` 已跟踪状态文件 | `doctor` WARN，给出 `git rm --cached -r` | 按提示解除跟踪；已在库里的历史证据按需清理 |
| 钩子只有起始标记、没有结束标记 | `install-hook` rc=1，**不改原文件** | 手工删除残留标记或恢复钩子，再重装 |
| 钩子存在但不是本团安装 | `doctor` WARN「pre-commit 被他方占用」 | 不要覆盖；让事务官与用户确认能否合并两段钩子 |
| 不在 git 仓库 | `doctor` WARN，钩子装不了 | 先 `git init`；在此之前由主理人手动跑闸门 |
| `verify --force` 且零任务 | 放行但显式 WARN「零任务」 | 汇报里说明；能补回 TASK 就补，别把 force 当常规路径 |
| 出现 Python Traceback | 顶层兜底转成 `INTERNAL-ERROR` + rc=1 | 复制完整输出回报专家团；**不得**据此声称闸门通过 |

**排障固定顺序**：`python <sop_gate.py> doctor --root <项目根>` → 按 FAIL/WARN 逐项修 → 重跑出问题的那道闸 → 再继续。禁止「报错就跳过闸门」。

## 三、团队协作异常矩阵

| 症状 | 兜底动作 |
|------|---------|
| 开场卡片工具不可用 | 正文编号列表，**每次只问一项**，等用户回复再问下一项；不得假装已弹卡 |
| 用户首条信息已完整 | 跳过问询直接路由；只补缺失项；阵容自动判断并一句话说明 |
| `团队编排` / 调度 工具不可用或失败 | 停止建团，**如实说明工具不可用**；可提供单 agent 直调或纯主理人模式（此时明确声明「未经成员独立产出」），不得模拟成员发言 |
| 成员无响应 / 超时 | 主理人重发一次明确任务（含输入与期望产出）；仍未果则换同能力成员或由主理人**标注为「未取得该专业结论」**后请用户决定，不得代写结论 |
| 两名成员结论冲突 | 不自行撮合。把冲突点、各自依据（`file:line` / 命令输出）并列给用户拍板；安全/数据类冲突按更保守结论执行 |
| 成员给出的结论无 `file:line` / 无命令输出 | 退回该成员补证据；补不出则不计入采信 |
| 成员改了同一文件（编辑主权冲突） | 停手 → 重读当前内容 → 报告差异给用户 → 不回滚他人改动 |
| 用户中途改需求 / 扩范围 | 标 `⚠️` 回 Phase 1，重新冻结 Goal/Done/Out of scope 并重新 `approve`；不得在当前 TASK 里静默追加 |
| 用户要求跳过闸门 / 说「差不多就行」 | 说明硬约束语义；若仍坚持，只在用户**明确**同意后用 `--force` 并在汇报中写下跳过项与风险 |
| 会话中断 / 上下文丢失 | 新会话先跑 `status` + `doctor`，再按 `ACTIVE` / `NEXT` / `followup` 恢复；不凭记忆断言进度 |
| skill 引用文件缺失 | 按「插件不完整」处理，先 `doctor`；不得凭记忆补写 skill 内容 |
| 情绪类请求（我快崩了） | 调 morale-booster 一次 1–3 句；用户明确说「安静点」则不调；鼓励不替代 SPIKE 立项 |

## 四、降级模式（Degraded Mode）

只有当**工具/环境确实不可用**时才允许进入，且必须同时满足：

- ✅ 向用户说清楚：缺的是什么、哪道闸从硬变软、影响范围；
- ✅ 所有能跑的闸门照常跑，输出照常贴；
- ✅ 明确写出「本次未经 XX 闸门验证」；
- ❌ 不得伪造命令输出、成员发言、测试结果、批准日期；
- ❌ 不得在降级模式下声称「全流程已闭环」。

退出降级：补齐环境 → `doctor` 全绿 → 从**出错的那道闸**重新跑起，已标 ✅ 的任务不受影响。

## 五、异常上报模板

```
现象：<一句话>
命令 / 阶段：<sop_gate.py xxx 或 Phase N>
退出码：<rc>
完整输出：<原样贴，含 stderr>
已尝试：<按本手册哪几步>
项目根 / 环境：<root、OS、Python 版本>
```

主理人收集到这份模板后，按「闸门 → 脚本 → 文档」三层定位；确认是脚本缺陷的，补回归用例（tests/test_sop_gate.py）再修实现，全绿后才打包。
