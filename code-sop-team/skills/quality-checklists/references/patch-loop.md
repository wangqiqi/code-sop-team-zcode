# 补丁循环拦截清单

专治**「同一个 bug 修了三四轮还没修好」**。这份清单的用途不是判断代码好不好，而是判断**现在该不该继续打补丁**。

## 为什么单独立这一份

打补丁的成本是复利的：第 1 轮改一行，第 2 轮加个 if，第 3 轮绕过检测，第 4 轮整个模块都在为这个 bug 让步。到了这一步，问题已经从「一个 bug」变成「架构没对齐」。继续 patch 只会把债务固化。

所以规则是硬的：**同一症状出现 ≥2 次，停止 patch，转 SPIKE 立项。**

## 一、触发判据（命中任一即升级）

| 信号 | 判据 |
|---|---|
| 同 TASK 验收失败 ≥2 轮 | `sop_gate.py task-verify` 已记 `followup` 计数，脚本会直接提示 |
| 同一症状换位置复现 | 上周是上传失败，这周是导入失败，根因都是类型判定 |
| 补丁需要「绕过」既有检测 | 为了过测试而放宽断言、注释掉校验、加白名单特例 |
| 修 A 导致 B 挂，修 B 又导致 A 挂 | 典型的真相源不唯一 |
| 补丁引入新的魔法分支 | 新增 `if (specialCase)` 且无法用领域语言解释 |
| 两次以上改同一行附近 | `git log -L` 显示同一函数被反复触碰 |

**命中后禁止的动作**：继续加判断、加大 try/except 范围、把失败路径改成静默、调低断言强度。

**必须的动作**：标 `⚠️` 回规划，由规划师立 `SPIKE-*`，把「根因假设 + 验证方式」写清，调研完再回来拆 TASK。

## 二、五个高频反复区（对照自查）

这五类问题占了「反复打补丁」的绝大多数。改到相关代码时先扫对应项。

### 1. 异步进度（API 写 + Worker 写 + 前端读）

- [ ] 进度有**单一真相源**；多存储时 `get` 按 `updated_at` 取较新者 — **Blocker**
- [ ] 写失败**不静默**：共享存储不可达/超时 → ERROR 日志 + 可观测字段 — **Blocker**
- [ ] 对共享存储的 `get/set/publish` 有**有限 timeout**（3–5s），禁止无限 await 挂死请求线程 — **High**
- [ ] 任务 ID 契约在所有 create/fallback 路径一致；新增 fallback 已 grep 全链路 `get(id)` — **High**
- [ ] 改 progress store 补了「实例 A 写 → 实例 B 读」测试 — **High**
- [ ] 关键发布/同步失败有持久化重试队列，不靠内存重试（进程重启丢单）— **High**

**典型症状**：Worker 已 `failed`，API 仍返回陈旧 `running 0%`。

### 2. 长任务 UI（上传/导入/安装向导/批量同步）

- [ ] 阶段是**显式枚举**（`upload | extract | persist | done | failed`），非散落布尔组合 — **High**
- [ ] 完成/失败态不因 `loading=false` 卸载面板，用户能看到结果 — **High**
- [ ] 阶段进度**不回跳**（后端启动帧 `done=0` 不得让已达 100% 的父阶段倒退）— **High**
- [ ] 成功后触发列表 refetch（同一 hook 封装 `refreshAfterComplete`）— **High**
- [ ] 可取消 · 可重试 · 有速率/ETA（至少给出口，不干等）— **Medium**
- [ ] 跨分钟级任务在最终提交前校验/刷新 token；401 只自动续期一次 — **High**

**典型症状**：「传完了但列表里没有」「进度条卡 0% 假死」。

### 3. 弹窗分层（z-index）

- [ ] z-index 来自**集中令牌表**，组件内无 magic number `9999` — **High**
- [ ] 层级语义固定：内容 < sticky < 普通层 < 工作流层 < 破坏性确认 < 全屏进度 < 决策层 < toast — **High**
- [ ] 长任务 + 决策并存时，规格写明**谁在上**（打开决策层时进度层隐藏或降权）— **High**
- [ ] 新功能没有私自抬 z-index 压过既有层 — **Medium**

**典型症状**：「进度 0% 以为后台没启动，其实是确认弹窗被挡住了」。

### 4. 错误上下文

- [ ] 内层已写详细错误时，外层**禁止**用裸 `str(e)` 覆盖 — **Blocker**
- [ ] 看门狗超时写入与业务失败的**覆盖优先级**写清（谁先写、谁可覆盖）— **High**
- [ ] 前端 failed 态能读到最终 `error_message` / `detail` — **High**
- [ ] 全局 exception handler 返回体含 `error` 或 `detail`，与前端 errorHandler 一致 — **High**
- [ ] 日志可含 stack；返回用户友好句 + `error_code`，不暴露内部路径/密钥 — **High**

**典型症状**：「只显示服务器内部错误，日志里明明有原因」。

修 hotfix 时 grep 所有 `_update_*_status` · `setFailed` · `catch` 链。

### 5. 单一检测器（格式/MIME/协议/版本判定）

- [ ] 「这是哪种 X」只有**一处实现**，路由 A/B、preview、Worker 全都 import 同一函数 — **High**
- [ ] 双后缀优先（`.tar.gz` 在单后缀规则之前匹配）— **High**
- [ ] 无后缀路径有 fallback（魔数 + 会话原始 filename），不误杀 — **High**
- [ ] 可选依赖未安装时给**可行动**提示（包名/安装命令），非笼统 `invalid` — **Medium**
- [ ] 改 detector 后全库 grep 旧判定函数，补扩展名 × 魔数 × 边界矩阵测试 — **High**

**典型症状**：「preview 认、upload 不认」——历史高频重复劳动源。新增第二种检测逻辑必须立 SPIKE 或在 Out of scope 写明「复用现有 detector」。

## 三、范围纪律（防顺手扩张）

补丁越修越大，通常是因为顺手改了无关的东西。改前对照：

- [ ] 只动 ACTIVE 任务或用户明确请求的范围 — **High**
- [ ] 不碰 Sprint **Out of scope**；「顺便」重构/格式化全库/重命名无关标识符 → 单独 TASK — **High**
- [ ] 修的是**根因**，不是 symptomatic patch — **High**
- [ ] 没有新增「只被调用一行」的 helper，没有过度抽象 — **Medium**
- [ ] 命名描述意图，无 `d` / `x` / `tmp`；魔法数字提为命名常量 — **Medium**
- [ ] 没有无理由自研轮子（有宽松开源同类时优先依赖或 vendor）— **Medium**

**可扩大范围的唯一三种情况**：用户明确 steer；不扩大则无法通过 `task-verify`；plan.md 已更新 Goal。

## 四、结论怎么给

| 观察 | 建议 |
|---|---|
| 首轮失败，根因清楚 | 继续修，正常走 `task-verify` |
| 第 2 轮仍失败，或命中任一触发判据 | **不放行**，建议立 `SPIKE-*`，写清根因假设与验证方式 |
| 已 3 轮以上 | **强停**，把该 TASK 拆开或整体回规划（Phase 1）重设 Goal 与验收 |
| 补丁本身引入新魔法分支 | 计 **High**，要求先把分支的领域含义写进 plan 再实现 |

- 建议必须带证据：失败轮次、`task-verify` 输出、`git log` 片段。
- 判断「该不该继续」是本清单的唯一职责；跑不跑绿仍由 `sop-gate` 说了算。
