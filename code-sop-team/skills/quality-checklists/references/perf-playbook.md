# 性能排查手册

## 顺序

| 步 | 动作 | 产出 |
|----|------|------|
| 1 测量 | profiler、慢查询日志、LCP / FCP（前端） | 基线数据 |
| 2 假设 | 从数据挑一个瓶颈，改一处 | 单点变更 |
| 3 再测 | 同条件复测 | 前后对比 |
| 4 文档化 | 记录前后数据 | 可复核结论 |

- [ ] 先测量再改，不凭直觉优化 — **High**
- [ ] 一次只改一处，改完立刻复测 — **High**
- [ ] 前后数据写进结论，不写「感觉变快了」— **High**
- [ ] 不做 premature optimize；无实测证据的项不立项 — **Medium**

## 常见瓶颈清单

- [ ] N+1 查询 — **High**
- [ ] 缺索引 — **High**
- [ ] 同步 I/O 在 hot path — **High**
- [ ] 过大 bundle / 无 code split（SSR 场景同时看服务端渲染开销）— **Medium**
- [ ] 首屏指标（LCP / FCP）未纳入测量 — **Medium**

## 输出格式

| 字段 | 要求 |
|------|------|
| **瓶颈** | 位置 `file:line` |
| **证据** | 测量数据 / profiler 输出 / 慢查询日志 |
| **建议** | 改法 + trade-off |

- [ ] 每条瓶颈都能落到 `file:line` — **High**
- [ ] 建议附 trade-off（复杂度 / 内存 / 可维护性）— **Medium**
- [ ] 无证据的猜测标为待验证假设，不作为结论 — **High**

## 边界

- 只做排查与建议；架构级改动回流规划（Phase 1），不在排查中擅自大改。
- 性能问题本质是 bug：先按调试循环复现，再测量。
- 结论回主理人，是否立项由规划决定。
