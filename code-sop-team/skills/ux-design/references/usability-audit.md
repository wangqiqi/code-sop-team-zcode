# 可用性走查（UI Sprint 收尾跑）

按顺序走，不要跳：

- [ ] 新用户视角：不看文档，能否在 30 秒内完成核心任务 — **Blocker**
- [ ] 每个数据界面六态齐全 — **Blocker**
- [ ] 多角色的"不该看到"已实现（不只是隐藏按钮，接口也要挡）— **Blocker**
- [ ] 一屏一个主按钮；主次动作视觉可分 — **High**
- [ ] 空态有引导，不是一片白 — **High**
- [ ] 错误态给可执行动作，不是只有错误码 — **High**
- [ ] 导航深度 ≤3；无平级双入口 — **High**
- [ ] 1280 / 1440 / 1920 三档宽度无错位、无横向滚动条 — **High**
- [ ] 深色模式下文字对比度达标 — **High**
- [ ] 间距/字号/颜色来自 token，无 magic number — **Medium**
- [ ] 键盘可达：Tab 顺序合理、焦点可见、Esc 能关弹窗 — **Medium**

**多角色系统的"只隐藏按钮"一律计 Blocker**——那是安全漏洞，不是体验问题。

## 分级标准

| 级别 | 判据 | 处理 |
|---|---|---|
| **Blocker** | 用户办不成事，或存在越权/数据泄露 | 不收口，必须修 |
| **High** | 能办成但会卡住、会误解、会重复操作 | 本次 Sprint 修 |
| **Medium** | 不影响任务，影响一致性与长期维护 | 进候选表 |

## 三个「假通过」的坑

走查最容易自欺的三处：

1. **用管理员账号走一遍就签字**。多角色系统必须每个角色都走，尤其"不该看到"那列。
2. **数据是满的时候看空态**。空态必须在真空白环境看，否则你看到的是有数据的正常态。
3. **本地网络很快时看加载态**。限速到 3G 再看一次，骨架屏和进度才会暴露问题。

## 走查记录格式

```
走查范围：<哪些页面 / 哪个角色 / 哪档宽度>
Blocker：<n 条，每条 界面 + 现象 + 期望>
High：<n 条>
Medium：<n 条>
未覆盖：<哪些页面没走 + 原因>
结论：<可收口 / 需整改后复走>
```

**未覆盖必须写。** 漏走而没记录 = 假装走过了。
