# 六态设计（漏一个就是 bug）

任何承载数据的界面，六个状态都要画：

| 态 | 要求 | 常见错误 |
|---|---|---|
| **空（首次）** | 告诉用户这里是什么、怎么开始 | 一片白，用户以为坏了 |
| **空（有筛选无结果）** | 说明是筛选导致，给"清除筛选" | 与首次空态混用同一句话 |
| **加载** | 骨架屏或明确进度；超过 1s 必须给反馈 | 转圈转 10 秒无进度 |
| **错误** | 说清什么错了 + 可执行动作（重试/返回） | 只显示"服务器内部错误" |
| **成功** | 结果可见，列表已刷新 | 提示成功但列表没变 |
| **无权限 / 不可用** | 说明原因与申请路径 | 报 404 让用户以为页面没了 |

## 两个空态必须分开

首次空态和筛选空态混用是最高频错误：

| 场景 | 该说什么 |
|---|---|
| 首次（库里真没有数据） | 「还没有巡检记录。点击右上角『新建巡检』开始。」→ 给创建动作 |
| 筛选后无结果 | 「当前筛选条件下没有记录。」→ 给「清除筛选」，**不给创建** |

给错会让用户以为数据丢了，或者反复创建重复数据。

## 长任务另加四条

上传 / 导入 / 批处理 / 导出 这类超过 3 秒的操作：

| 要求 | 说明 |
|---|---|
| **可取消** | 用户有权中止；不能取消要说清楚为什么 |
| **可重试** | 失败后能重试，且重试不造成重复提交 |
| **进度不回跳** | 进度条只能前进；从 80% 退回 20% 比没有进度更伤 |
| **离开不丢** | 切页面回来，任务还在跑且有结果 |

细节见 `quality-checklists/references/patch-loop.md` 的长任务 UI 一节。

## 状态矩阵（自查用）

对每个数据界面填这张表，空格就是缺的：

| 界面 | 首次空 | 筛选空 | 加载 | 错误 | 成功 | 无权限 |
|---|---|---|---|---|---|---|
| 订单列表 | ✅ | ⬜ | ✅ | ✅ | ✅ | ⬜ |
| 详情页 | — | — | ✅ | ⬜ | ✅ | ⬜ |

「—」表示该态不适用，必须能说出不适用的理由。

## 为什么这条最值得较真

六态是「功能做完了」和「能给人用」之间的分界线。演示时数据是满的、网络是好的、账号是管理员——**三个条件同时成立才只需要一个态**。真实环境永远不会。
