# ADR · 演进与技术债

## 一、ADR（架构决策记录）

每个**不可轻易回退**的决定都写一条。放 `docs/adr/NNN-<slug>.md`：

```markdown
# ADR-003 用 SQLite 而非 Postgres 作为本地存储

## 状态
已接受（2026-11-18）

## 背景
家庭局域网单机部署，无运维，数据量 < 10 万行，需要零配置启动。

## 决策
用 SQLite + WAL 模式；迁移脚本纳入版本管理。

## 代价（必须写）
- 并发写受限，多写入方需串行化
- 无内置备份，需自建定时快照
- 迁移不能在线执行，需停机窗口

## 替代方案与被否原因
Postgres：需独立进程与运维，超出"装完即用"的约束。

## 何时该重审
并发写入方 > 2，或数据量 > 500 万行。
```

**没有"代价"一节的 ADR 是宣传稿，不是决策记录。**

### 什么时候必须写 ADR

| 情形 | 例子 |
|---|---|
| 引入新的基础设施 | 加缓存、加队列、换数据库、加反向代理 |
| 改变依赖方向 | 把领域逻辑上移到控制器、把 UI 逻辑下沉到 service |
| 定死对外契约 | 公开 API 的 URL 结构、错误码体系 |
| 选择"不做"某个明显做法 | 决定不用 ORM、决定不做微服务 |
| 一次性迁移策略 | 大表拆分、数据回填方案 |

不需要写 ADR 的：命名、目录微调、单个函数实现方式——这些进 PR 描述就够。

## 二、演进与技术债

- 允许欠债，但必须**记账**：写进 plan 的候选表或 `docs/tech-debt.md`，含触发条件。
- 技术债条目格式：`<位置> · <欠了什么> · <现在为什么能欠> · <什么条件下必须还>`。
- 禁止的欠债方式：口头说"以后重构"、注释写「待重构」类标记但无记录、用临时方案覆盖后不留痕。

### 技术债条目示例

```
src/orders/export.ts · CSV 导出全表加载进内存 · 当前订单量 < 1 万行，内存够 ·
单次导出超过 5 万行前必须改成流式
```

有触发条件的债是**可管理的**；没有触发条件的债是**遗忘**。

## 三、大改造能不能分步

大改造前先回答：**能不能分步走？每一步结束时系统都是可用的吗？** 不能就是大爆炸改造，要拆。

拆分三原则：

1. **每步可独立上线**：上一步不做完也能跑，只是能力少一点。
2. **每步可独立回滚**：出问题回退一步，不用回退整批。
3. **新旧可共存一段时间**：双写、双读、开关切换，而不是一刀切。

做不到这三条 → 说明改造范围切错了，回去重切，不要硬推。

## 四、重构的判断门槛

| 情况 | 处理 |
|---|---|
| 要改的代码没有测试 | 先补特征测试（characterization test），再动结构 |
| 只改一处就要动 5 个文件 | 边界错了，先立 REV 任务讨论边界，别硬改 |
| 用户说"顺手重构一下" | 拒绝顺手：立独立任务，独立验收，独立 commit |
| 改完无法证明行为不变 | 不算重构，算重写——按新功能走完整流程 |
