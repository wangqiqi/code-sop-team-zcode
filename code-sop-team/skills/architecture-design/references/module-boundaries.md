# 边界划分 · 依赖方向 · 接口契约

## 一、边界划分

**好的边界只有一个特征：改一处不牵连别处。**

划分时看四件事：

1. **变化频率**：经常一起改的放一起，改动节奏差一个数量级的必须分开。
2. **数据所有权**：一张表只归一个模块写。多个模块都写同一张表 = 边界没划。
3. **依赖方向**：业务逻辑不依赖 UI，UI 不依赖数据库驱动；依赖只能单向。
4. **可替换性**：换掉这个模块的实现，其他模块要不要改？要改就是耦合。

### 反模式（看到就打回）

| 反模式 | 症状 | 后果 |
|---|---|---|
| 上帝模块 | 一个 service 被 10 个地方 import | 谁都不敢改 |
| 循环依赖 | A 引 B、B 又引 A | 打包/加载失败，测试难写 |
| 共享可变状态 | 两个模块读写同一个全局/单例 | 时序 bug 不可复现 |
| `util` / `common` 垃圾桶 | 什么都往里塞 | 变成隐形的上帝模块 |
| 按技术分层切业务 | `controllers/` 里放 5 个业务域 | 改一个业务要动 5 个目录 |

## 二、依赖方向

画一条线，箭头只能往一个方向走：

```
入口（UI / HTTP / CLI）
        ↓
应用层（用例编排）
        ↓
领域层（业务规则，不依赖任何框架）
        ↓
基础设施（数据库 / 外部 API / 文件）
```

**领域层不许反过来 import 框架代码。** 出现 `import React` / `from fastapi import` 在领域层，方向就反了。

检查方法：`grep` 领域目录里的框架 import，有一条就是一处债。

### 各栈的具体检查点

按文件类型查 `stack-conventions` 的对应文件（`web-frontend.md` / `backend.md` / `systems.md`），每个栈都有「通用铁律」与「完成判据」两节，那里能看到该栈典型的依赖倒置写法。

## 三、接口契约

跨模块/跨服务/前后端之间的契约，**先定形状再写实现**：

- 输入：类型、必填、边界（上下限、枚举白名单）
- 输出：成功形状、失败形状（error code 稳定，不只给 message）
- 幂等性：这个操作重放两次会怎样？
- 版本策略：破坏性变更怎么隔离

契约五面（server / client / mocks / openapi / CHANGELOG）必须同步改，只改一半是线上事故第一来源。审查清单见 `quality-checklists/references/api-contract.md`。

## 四、单一真相源（single-detector）

同一个判断在代码里只能有一处实现：

- 状态判断、能力探测、权限判定，**只允许一个函数说了算**。
- 出现第二处相似的判断 → 要么合并，要么明确谁是主、谁是缓存。
- 症状：修了一个地方另一个地方还是旧行为——典型的双真相源。

这条不是洁癖：双真相源会让「改了没生效」变成不可诊断的 bug。
