# 数据层（schema / 迁移 / 索引 / 备份 / 一致性）

**数据工程师主力文件。** 铁律：**不可逆操作，先给回滚路径。**

## 一、schema 变更

- 一次迁移只做一件事（加表 / 加列 / 改类型分开）。
- **加列必须有默认值或允许 NULL**，否则历史行会炸。
- 删列/改名分三步：加新列 → 双写并回填 → 停用旧列（至少跨一个发布周期再删）。
- 迁移脚本**必须可回滚**（down 脚本与 up 同等对待，同等测试）。

### 迁移三段式

| 段 | 内容 | 验收 |
|---|---|---|
| up | 建/改/回填；分批处理大数据量 | 在副本库跑通，行数与预期一致 |
| down | 精确反向；删不掉的数据要说明 | 跑完 down，表结构与迁移前 diff 为空 |
| verify | 校验查询（行数、空值数、枚举分布） | 输出具体数字，不是"看起来对" |

## 二、索引

- 先看执行计划，再加索引。`EXPLAIN` 显示全表扫才是缺索引。
- 条件里对列用了函数/类型转换 → 索引失效，先改查询再考虑建索引。
- 联合索引看最左前缀；不要为每个字段单独建索引。
- 索引有写成本：写多读少的表慎加。

### 判断顺序

```
查询慢？
  → 抓慢查询的具体 SQL
  → EXPLAIN 看是否全表扫 / 是否用错索引
  → 是查询写法问题？改查询（函数、隐式转换、SELECT *）
  → 是确实缺索引？按 WHERE/JOIN/ORDER BY 的最左前缀建
  → 加完再看一次 EXPLAIN，确认 hit
```

**不加索引就跑 benchmark 是浪费；加了索引不回头看执行计划是自欺。**

## 三、备份与恢复

- 改数据前问三句：**备份在哪？回滚脚本写了吗？出问题多久能恢复？**
- 备份要**验证过能恢复**才算备份。没验证过的备份等于没有。
- 破坏性操作（DROP / TRUNCATE / 大批量 UPDATE）必须：先 dry-run 数出行数 → 确认 → 执行 → 校验行数。

### 破坏性操作五步

1. `SELECT COUNT(*)` 锁定影响面，把数字贴给用户确认。
2. 备份（并验证能恢复）。
3. 事务内执行，或分批带 LIMIT。
4. 执行后 `COUNT(*)` 对比。
5. 数字不符 → 立即回滚，别"再看看"。

## 四、一致性与幂等

- 写路径尽量幂等：用唯一键/去重表，而不是"应该只调用一次"。
- 跨表/跨服务写，要么事务，要么补偿；不允许"一半成功"的静默状态。
- 数据修复脚本要能重复执行且结果一致（幂等脚本），不然修一半失败就没法重跑。

### 幂等的三种实现

| 方式 | 适用 | 注意 |
|---|---|---|
| 唯一键 + upsert | 单表、有天然唯一标识 | 冲突时明确覆盖还是忽略 |
| 去重表 / 处理记录 | 跨服务、异步 | 记录要带时间与来源 |
| 状态机（只允许某些跃迁） | 流程型数据 | 跃迁表要写进 ADR |

## 五、回传格式（数据变更）

```
变更：<加表/加列/改类型/回填>
up / down：<分别做什么>
影响面：<表 + 预估行数 + 是否有锁表风险>
备份：<在哪 + 是否验证过恢复>
回滚路径：<怎么退 + 退多久>
校验查询：<具体 SQL + 期望结果>
不可逆点：<哪一步做了就退不回 + 缓解措施>
```
